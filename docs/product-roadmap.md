# Product improvement plan

This is an ongoing improvement program, not a declaration that the product is complete. Henry++ and upstream contributor attribution, GPL terms, user settings, and the existing memory-cleaning safety checks remain requirements throughout.

## Acceptance targets

| Area | Required outcome | Evidence needed |
| --- | --- | --- |
| Permissions | Previously authorized users can reopen without repeated UAC; first-time consent, revocation, unsafe paths and failed task launches remain explicit | Installed-app exit/reopen, disabled/missing task, non-admin account and writable-path checks |
| Installation | Custom locations, upgrades, relocation instructions, uninstall and settings preservation work consistently | Real fresh install and upgrade on a second drive, settings hashes, task and uninstall registration |
| Size | Reduce download, installed and build-cache footprints without breaking clean-machine startup or hiding dependency downloads | Measured before/after size, clean-machine startup, both languages, configuration and cleanup paths |
| Interface | Compact Magpie-inspired layout, 10–12 physical-pixel corners, readable controls and coherent states | Light/dark, Chinese/English, narrow windows, 100–200% scaling, keyboard and input-focus checks |
| Cleanup | Accurate results, visible busy/failure state, no overlapping cleanups, conservative automatic behavior | Existing engine checks plus separately authorized real cleanup and fullscreen-game scenarios |
| Updates | Background download, clear progress, safe cancellation/retry, one restart at installation and preserved settings | Download interruption, digest mismatch, upgrade cancellation and real successful update |
| Maintenance | Reproducible build, private author identity, upstream credit and documented release evidence | Clean build, scoped English commits, release asset verification and source/tag consistency |

## Confirmed priorities

1. Manual reopen now reuses an existing authorized login task and waits for an elevated window to respond. Routing and timeout checks pass; real installed-app consent/reopen validation remains pending. Cleanup/import/update helper arguments are excluded.
2. Build scripts now limit running-process guards to output directories, while rejecting inaccessible process paths. The separate installed copy no longer blocks the fixed preview build.
3. Installation size is primarily bundled runtime code. The 0.0.2 staging directory includes a roughly 25 MiB Windows SDK projection, 15 MiB .NET core library and 15 MiB WinUI native DLL. Measure a supported trimming strategy before changing release defaults; do not delete runtime DLLs manually.
4. A custom user-writable installation currently loses persistent elevated startup and automatic update installation. Investigate a small protected helper design that preserves user-chosen UI locations without granting elevated execution to replaceable files. Current permission checks must remain until a complete design and validation replace them.
5. Inspect the current real UI and consolidate permission/update status text. Validate readability rather than treating successful compilation as visual approval.

## Implemented in the next-version source

- Five-minute physical/committed memory trend with bounded storage (301 samples), session-only retention, accessible text summary, and explicit gaps after interrupted sampling.
- Usage-state label, stronger secondary-text contrast, restrained 12px grouping cards and 10px controls. The cleaning action remains above the chart and visible in the default-size window.
- Returning from scrolled settings resets the overview to its top after layout/focus changes settle. Input callbacks stop during window teardown.
- The history fixture images use synthetic data exclusively inside the developer self-check. Regular UI always uses native measurements.

Next priorities: asynchronous shutdown boundaries, actual installed permission reuse, and measured idle runtime costs. Keep new diagnostics read-only by default and avoid process-killing features.

The settings hierarchy now keeps the three original cleanup areas visible and groups the five additional areas under an expander with a selected count. Existing enabled advanced choices expand automatically on launch. Download progress is bounded to percentage changes, reports size, and exposes cancellation without leaving an executable partial download. Permission descriptions distinguish session-only consent from an authorized startup task.

Settings/update checks passed in Chinese and English, including 48 layout cases with the longer installed-permission descriptions. Real file-copy checks cover intermediate progress and cancellation after a partial write. The final shutdown guard and end-of-copy cancellation check were rebuilt and rechecked in Chinese. Download-state screenshots use a fixture; no network transfer or installer execution is implied.

Initial microbenchmark on the development machine: native sampling averaged 0.104 ms per call; a populated 282-sample graph required 5.060 ms and approximately 335,751 managed bytes per geometry preparation. This excludes composition and is not an idle CPU benchmark. Reduce graph geometry allocations before adding more per-second visuals.

The graph now uses one polyline per uninterrupted series instead of one WinRT segment per sample. The same check measured 0.651 ms and 82,926 managed bytes per frame (approximately 87% less preparation time and 75% fewer managed allocations). The Chinese self-check passed all 18 groups and 48 layout cases after the change; data-gap assertions still pass. Timing is machine/load dependent.

Recent cleanups now retain the last five native attempts in memory for the current session. They show manual/automatic origin, duration, the observed available-memory increase, and partial/failed outcomes. Confirmation or UAC cancellation does not create a fake cleanup record. Chinese and English checks passed 19 groups and 48 layout cases, including bounded retention and failure rendering. Fixture images were inspected; no real cleanup was invoked.

Shutdown now cancels an in-flight release check as well as a download, and ignores asynchronous startup/update/dialog results after exit. Sampling and cleanup entry points reject teardown work; developer self-check mode cannot invoke native cleaning through the window. Startup switch completion refreshes the permission description immediately. The incremental build passed without warnings, and Chinese/English checks passed 20 groups and 48 layouts each. This includes a pre-canceled release request that performs no network access; real UAC/task lifecycle acceptance remains separate.

An optional process overview reads the eight largest working sets on first expansion or manual refresh. It runs off the UI thread, releases every process object, skips exited/inaccessible processes, preserves the previous snapshot on failure, and performs no background enumeration or process termination. [Working sets include shared pages](https://learn.microsoft.com/en-us/dotnet/api/system.diagnostics.process.workingset64), so the UI explicitly avoids presenting their sum as system usage. Chinese/English checks passed 21 groups and 48 layouts; a real read took approximately 18 ms in one run. Render fixtures contain synthetic names, not a published inventory of local applications.

The real 0.0.3 staging executable at source `f45d25d` was measured as a normal unelevated process minimized to its actual tray, without a staging settings file. After five seconds of warmup, a 30-second sample on a 22-logical-processor machine consumed 125 ms of CPU: 0.416% of one core, or 0.019% of total machine capacity. Working set was 171 MiB and private committed memory 90 MiB. This is a short machine-specific observation, not a long-duration leak test; it includes shared runtime pages in working set and predates the optional process overview. No real cleanup, task registration or user settings writes occurred. The inspection process was stopped after measurement. The WinUI/runtime memory footprint remains a material product cost.

## Size experiment boundary

An isolated .NET 10.0.402 partial-trimming experiment reduced the publish folder from 178,340,120 to 87,032,681 bytes. It was **rejected for delivery**: the executable exited with `0xC0000005` before producing a self-check report. Analysis also warned about dynamic COM, reflection-based serialization and WinRT projections. Normal builds remain untrimmed and unchanged; do not enable trimming just to reproduce the smaller number. See Microsoft's [known trimming incompatibilities](https://learn.microsoft.com/en-us/dotnet/core/deploying/trimming/incompatibilities).

The experiment log and size/exit-code manifest were preserved in local work files. Automatic approval rejected cleanup of `D:\tmp\memreduct-tray-build\trim-experiment` with only `blocked by policy`; that directory remains and must not be deleted through an alternate mechanism. It contains temporary build outputs, not user settings. This cleanup restriction does not block normal development.

Validation for this iteration: the incremental build completed with zero warnings/errors. Chinese and English self-checks passed 18 check groups and 48 layout cases each, including scrolling back from settings and a visible primary action at the default window size. Offscreen light/dark renders were generated; Chinese and English overview renders were inspected. The installed and portable settings hashes match the pre-iteration baseline. No real cleanup, task mutation, install or release occurred during these checks.

## Native AOT assessment

Windows App SDK documents [Native AOT support](https://learn.microsoft.com/en-us/windows/apps/windows-app-sdk/release-notes/windows-app-sdk-1-6), but the current startup implementation still activates `Schedule.Service` through `GetTypeFromProgID`, `Activator.CreateInstance`, dynamic dispatch and runtime COM wrappers. [.NET Native AOT excludes built-in Windows COM](https://learn.microsoft.com/en-us/dotnet/core/deploying/native-aot/), so enabling the publish flag alone would not preserve this application's startup behavior. A future AOT candidate must replace and validate that interop path, address serialization/WinRT analyzer findings, and repeat the installed startup and update checks before any size or memory claim. The local shell did not locate `vswhere`, `cl.exe` or `link.exe`; no C++ toolchain was installed and no AOT binary or benchmark was produced during this assessment.

## Current validation boundary

The next source revision skips chart geometry while the window is hidden, minimized or scrolled away, and refreshes when the chart returns to the viewport. Sampling and tray monitoring continue. Settings and downloaded update files now run under the same account's ordinary token, including across asynchronous continuations. Atomic settings writes use exclusive random temporary files; failed replacement preserves the original, and reads reject files over 64 KiB. Chinese and English preview checks pass 23 groups and 48 layouts each. This token check ran from an unelevated caller: actual linked-token access from an elevated application remains unverified. If Windows cannot supply a same-account limited token, user-data access fails with an explicit error instead of falling back to administrator writes; UAC-disabled configurations are not supported by that path.

An independent Windows CI workflow checks resource-key parity and publishes a locked .NET 10.0.402 x64 build with seven-day artifact retention. Its [first remote run](https://github.com/Duye0120/memreduct-winui/actions/runs/39780335515) passed at `c9d1d28`, including clean restore and publish. It does not install the application, run desktop acceptance, or publish a Release.

A second real tray-process measurement at `c9d1d28` again consumed 125 ms of CPU over 30 seconds (0.416% of one core, 0.019% of this 22-logical-processor machine). Working set ended at 172.6 MiB and private committed memory at 90.2 MiB; handle count stayed at 850 across the three samples. The same isolated, ordinary-permission staging procedure was used. These short observations do not establish long-running leak freedom or materially smaller runtime memory use.

Settings are now constructed once, on the first settings-page visit (`16c4555`), using a separate WinUI UserControl. All 41 named controls and 24 event bindings are retained. The existing checks verify tray preference changes before first use, initialization from those current values, and reuse of the same control tree. Initial construction took 44–48 ms in the local preview checks, excluding subsequent layout/rendering. A third isolated tray measurement ended at 172.0 MiB working set and 89.4 MiB private commit, with 109.375 ms CPU over 30.052 seconds (0.364% of one core, 0.0165% of this machine) and 871 handles stable across three samples. The differences are small and do not establish a material memory or CPU improvement; the retained benefit is deferring unused control creation at startup.

The native close path now prepares shutdown when closing-to-tray is disabled or unavailable, just like the tray Exit command. Preparation is idempotent, cancels pending update work and disables preference callbacks; queued layout, error-banner and language-restart continuations also stop after exit. The existing lifecycle check exercises the shared preparation method, canceled token and unchanged UI state. This is not a physical close-button or real network-cancellation acceptance test.

Manual elevation now checks the requesting SID before reading settings and waits for a two-way, session-local event handoff before allowing cleanup. The original UI remains available after rejected authorization or a failed handoff, and preference changes are locked during transfer. An ordinary child process rejects the request before loading settings. Identity and event contract checks do not replace a real same-account elevated transfer test; cross-account cleanup is intentionally unsupported.

The current local 0.0.3 candidate installer compiled successfully with Inno Setup 7.1.0 from source `242029d`. Both staged-executable self-checks passed 28 groups and 48 layouts, including mutex ownership, explicit startup-cleanup priority, per-operation cleanup failure dispatch, accurate failed/partial/completed results, persistent global notices and navigation restrictions during elevation or large-text layout. Failed-only attempts preserve the previous completion timestamp and do not attribute unrelated memory changes to cleanup. The installer is 46,284,912 bytes, compared with 47,107,420 bytes for 0.0.2 (1.75% smaller despite the added UI). LZMA2 ultra compression reduces download size only; it uses a 32 MiB installer decompression dictionary instead of the default 8 MiB. The normal application remains untrimmed. Installed and portable settings hashes remain unchanged. This is a local candidate, not a published release or proof of successful installation. The preceding UI revision passed independent Windows CI; the final startup-priority revision's run is still pending. Exact package identity and native dependency inspection limits are recorded in [candidate acceptance](acceptance-0.0.3.md).

A 320.3-second ordinary-permission tray observation of staged source `e5ecc1f` crossed the five-minute history capacity. CPU time was 531.25 ms (0.166% of one core / 0.00754% of the 22-processor machine); final working set was 170.7 MiB and private commit 89.6 MiB. GDI objects stayed at 82 across all sixteen samples, USER objects ranged from 25 to 27, and kernel handles from 835 to 850 without sustained growth. The process had no settings file, did not open settings, and performed no cleanup or startup registration. These results support low idle CPU and bounded handles during this observation, not overnight leak freedom or substantially reduced WinUI memory use.

The later UI source `bfaae17` was observed for 30.06 seconds: 93.75 ms CPU (0.312% of one core / 0.0142% of this machine), 171.69 MiB final working set, 89.39 MiB private commit and 886 handles at all three samples. The same ordinary-permission, isolated tray procedure was used. The different durations do not support a relative performance claim; the final startup scheduling change has functional checks but no separate idle benchmark.

Existing self-checks can exercise pure path/ACL rules, task XML, settings import, memory-engine contracts and offscreen layout. They do not prove real UAC consent, scheduled task activation, installed-app relaunch, actual cleanup, upgrade rollback, or clean-machine dependency availability. Keep those items open until tested at the appropriate level.

Only publish a release after its scoped changes and assets have been verified and release authorization is present. Intermediate improvements can be committed and pushed to the personal repository without creating upstream pull requests.
