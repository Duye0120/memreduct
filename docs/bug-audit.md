# 原版问题与改版核查记录

核查日期：2026-10-22。对象为本仓库 `modern/` 中的 WinUI 应用；根目录历史 Win32 工程和用户已安装的 Henry++ 原版未改动。上游 issue 是用户报告，不等于已证明的根因，也不代表本改版一定存在相同问题。

## 本次修复：持续高占用下反复自动清理

参考上游 [#288](https://github.com/henrypp/memreduct/issues/288)。此前改版已有 30 秒冷却，但如果清理后仍高于阈值，阈值模式会每隔 30 秒继续尝试，无法区分一次新的内存压力和持续未缓解的占用。

- 用已编译旧程序的 `AppSettings.IsAutoDue` 复现：自动阈值 90%，清理完成后持续占用 95%，30 秒时返回 `true`。
- 自动清理完成后仍超阈值，将下一次阈值重试推迟 5 分钟；失败路径同样应用这一规则。低于阈值或退避到期后重新允许触发。
- 冷却从清理完成时计算；慢速原生操作完成后仍保留完整的 30 秒间隔。
- 用户明确启用的定时清理不受阈值退避限制；手动清理、全屏保护和带星号区域过滤保持原有行为。
- 切换阈值开关、修改阈值会清除旧退避。运行状态只留在内存中，不增加设置字段或改写旧配置。
- 主界面以中英文说明阈值重试暂缓，避免误以为自动清理失效。

回归使用既有隐藏窗口自检，覆盖 30/60/299 秒不重试、5 分钟恢复、内存回落重新触发、定时清理独立、游戏保护优先、手动清理和完成后的冷却。验证不实际清理内存，不修改启动项或用户设置。

| [#312：清理时窗口无响应](https://github.com/henrypp/memreduct/issues/312) | 原版在窗口线程直接执行清理；改版已有 `Task.Run` 后台清理、重入保护和状态动画。后台执行不保证消除操作系统因全局清理而产生的停顿，尚未复现该报告的整机卡顿。 |

| [#281：虚拟内存显示不正确](https://github.com/henrypp/memreduct/issues/281) | 改版显示 `GetPerformanceInfo` 的 CommitTotal/CommitLimit，标注“已提交内存”，不混用分页文件占用。只读采样自检覆盖此字段；清理不承诺释放应用仍持有的已提交内存。 |

| [#249：旧窗口变空白](https://github.com/henrypp/memreduct/issues/249) | 原报告对应历史 Win32 界面。当前 WinUI 复用控件并只更新变化值；没有复现该空白窗口，也没有把界面重写记为该 issue 的已验证修复。 |
| [#191：高占用时崩溃](https://github.com/henrypp/memreduct/issues/191) | 报告缺少崩溃日志，不能确定根因。本次没有制造整机内存耗尽，不能宣称修复。 |
